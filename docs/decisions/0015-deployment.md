# 0015: Deploying v1

**Status:** Accepted  
**Issue:** #16

## Context

Previously, AgentOS ran as five separate processes on one machine. This was inconvenient for reviewers and made the project difficult to reproduce. The API also had no authentication of its own before M5.

I wanted a deployment that could start the complete system using one Docker Compose command, expose a single entry point, and demonstrate that the dashboard, backend, workers, database, Redis, and code-execution sandbox work together.

## What was built

- One backend image, with a `base` target for the API, scheduler and migration service, and a `worker` target that includes the Docker CLI.
- One dashboard image using Next.js standalone output.
- Caddy as the only publicly published service.
- A separate `docker-compose.prod.yml`, leaving `docker-compose.yml` for development infrastructure.
- A one-shot `migrate` service that applies database migrations and seeds the agents.
- A one-shot `sandbox-image` service that pulls the Python execution image before workers need it.
- A worker with access to the Docker socket, allowing it to launch isolated execution containers.
- Caddy routing the dashboard and API through the same origin, with HTTP Basic Authentication protecting every POST request.
- CI that builds the images, starts the stack, checks routing and authentication, and verifies Docker execution from the worker.

---

## 1. Same origin vs dashboard on Vercel and API elsewhere

I chose **same-origin deployment using Caddy**.

The dashboard and API are served through one entry point. The browser accesses the dashboard and API through the same host, rather than communicating with a separately hosted backend.

I chose this because it simplifies several deployment concerns:

- `NEXT_PUBLIC_API_URL` is baked into the Next.js build, so deploying the dashboard and API separately would require careful configuration of the API URL.
- A separate frontend and backend would require CORS configuration.
- WebSocket connections would need to work across separate origins, including handling secure `wss://` connections.
- Hosting the dashboard and backend separately would introduce another deployment provider, configuration and potentially another bill.

With Caddy, the browser communicates with one origin, and Caddy routes requests to the appropriate internal service. This also makes WebSocket routing simpler.

**The trade-off:** I have to manage the complete deployment myself, including Docker, Caddy, TLS configuration and the underlying host. I lose some of the convenience of deploying the frontend independently through Vercel.

For the local demo, I use `http://localhost:8080`. A real domain can be configured through Caddy to provide automatic HTTPS.

## 2. The Docker socket

The worker has access to `/var/run/docker.sock`, which allows it to create and manage Docker containers.

This is a significant security trade-off because Docker socket access is effectively root-equivalent access to the host.

### What attack does this enable?

If an attacker compromises the worker process, they could use the Docker socket to issue arbitrary Docker commands.

For example, they could attempt to start a privileged container and mount the host filesystem into it. This could allow them to access host files, secrets and potentially take control of the host.

The dangerous part is that the worker has more privileges than the code it executes.

### What makes this harder?

The architecture separates the trusted worker process from the untrusted agent-generated code.

The worker runs the agent loop and invokes the Docker CLI. The actual Python code generated by the Coder runs inside a separate, throwaway sandbox container.

The sandbox has:

- No network access (`--network none`).
- A read-only filesystem.
- A small temporary filesystem (`16 MB`, with `noexec`).
- No Linux capabilities (`--cap-drop ALL`).
- `no-new-privileges`.
- A non-root user (`65534`).
- A limit of 64 processes.
- 128 MB memory with no swap.
- One CPU.
- No host filesystem mounts.
- No host environment variables passed into the sandbox.
- A timeout and output-size limit.

The code is passed through standard input, and the container is removed after execution.

This means agent-generated code does not directly receive the Docker socket or access to the host filesystem.

However, these controls do not eliminate the risk of a compromised worker. The sandbox also shares the host kernel, so container isolation is not equivalent to a separate virtual machine.

### What would I do in M8?

M8 is intended to strengthen isolation and harden the execution infrastructure.

I would investigate stronger sandboxing technologies such as gVisor or Firecracker, reduce the worker's direct access to the host Docker daemon, and introduce stronger resource controls and execution monitoring.

The goal would be to reduce the impact of a compromised worker or a sandbox escape.

## 3. The login gate

The deployment uses Caddy HTTP Basic Authentication on every POST request.

### What does it protect?

POST requests can create missions and trigger operations that change application state.

The gate ensures that someone cannot simply send an unauthenticated POST request to the API and start missions.

### What does it leave open?

GET requests remain accessible without authentication.

This means mission information and other readable API resources are not protected by the login gate. It is not a complete user authentication or authorization system.

### Why is this acceptable for a demo but not a product?

For a local demo, the gate provides a simple barrier against unauthorized mission creation without requiring a complete authentication system.

For a real product, this is insufficient because users need individual identities, permissions and access boundaries. Basic Authentication on POST requests does not provide per-user authorization, ownership checks or proper access control over read operations and WebSocket connections.

### What replaces it in M5?

M5 is the security milestone. It introduces stronger capability-based permissions, a policy engine and tool guardrails.

The intention is to move beyond a deployment-level login gate toward application-level security and authorization. The exact user authentication and session mechanism still needs to be designed and implemented; it should not be considered complete in v1.

## 4. Why did the CI smoke test create a mission expected to fail?

The CI environment does not have access to a real LLM provider.

It uses a placeholder provider and model configuration, so a mission cannot complete its actual LLM planning stage.

However, creating a mission still allows CI to verify important parts of the deployment without depending on an external model API.

The test verifies:

- The Docker images can be built.
- The complete Compose stack can start.
- Database migrations and agent seeding work.
- The dashboard is reachable.
- The API is reachable.
- An unauthenticated POST request receives HTTP 401.
- An authenticated mission-creation request receives HTTP 202.
- The worker can communicate with Docker and start a Python execution container.

### What does it not prove?

It does not prove that the actual LLM planning, agent execution, reviewer workflow or complete mission lifecycle succeeds.

The CI Docker command also exercises Docker execution directly from the worker; it is not a substitute for testing every restriction in the actual `run_python` implementation.

### What would a real LLM integration test need?

It would need a reachable LLM provider with valid credentials and a real model configuration.

The test should:

1. Submit a mission.
2. Verify that the planner produces a valid DAG.
3. Verify that the correct agents are assigned.
4. Confirm that workers execute the tasks.
5. Confirm that tool calls, including Python execution, work.
6. Verify that the reviewer receives the coder's output.
7. Confirm that the mission reaches its expected final state.

This would be an end-to-end test of the actual LLM path rather than just the deployment infrastructure.

## 5. A restarted worker gets a new consumer name in containers

Redis Streams consumer groups track pending messages against individual consumer names.

If a worker restarts with a different consumer name, messages pending under its previous name may remain associated with the old consumer.

The new worker will not automatically receive those pending messages just by joining the same consumer group.

### What is the gap?

The current implementation relies on stable consumer names for recovery after a restart.

If the old consumer name never returns, pending messages can remain stuck until they are explicitly reclaimed.

### What fixes it in M4?

M4 introduces more reliable message recovery mechanisms, particularly:

- `XAUTOCLAIM` to transfer sufficiently idle pending messages to an active consumer.
- Leases and heartbeats to track whether a worker is still executing a task.
- Timeouts and retries to recover tasks abandoned by crashed workers.
- A sweeper to recover stale tasks and re-publish missing work.
- Dead-letter handling for messages that repeatedly fail.

Stable consumer names remain useful, but `XAUTOCLAIM` removes the dependency on the original consumer returning before pending messages can be recovered.

## 6. What did I not test?

The deployment was tested locally using Docker Desktop on Windows, and the CI workflow provides a separate Linux-based deployment smoke test.

However, several areas remain outside the scope of these tests:

- **Real production deployment:** I tested the local deployment, not a publicly hosted production environment with a real domain and automatic TLS renewal.
- **Real LLM integration in CI:** The CI environment uses a placeholder model configuration, so it does not verify the complete LLM-driven mission lifecycle.
- **Large-scale concurrency:** The deployment uses a small worker configuration. It has not been load-tested with many simultaneous missions and workers.
- **Worker crash recovery:** The M4 lease, heartbeat, retry and message-reclaim mechanisms are not yet implemented.
- **Hostile multi-user access:** The deployment does not yet have complete user authentication, authorization
